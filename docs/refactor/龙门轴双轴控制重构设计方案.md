# 龙门 X 轴双轴控制 —— 重构设计方案

> **文档日期**: 2026-06-06  
> **适用版本**: servoV6 (commit cd04517)  
> **问题域**: 龙门 X 轴的点动/位置移动/信息获取架构重构

---

## 1. 现状问题分析

### 1.1 当前架构概览

```
┌──────────────────────────────────────────────────────────────────────┐
│                          SystemContext                                │
│  ┌──────────┬──────────┬──────────┬──────────┬──────────┬──────────┐ │
│  │  Axis X  │  Axis X1 │  Axis X2 │  Axis Y  │  Axis Z  │  Axis R  │ │
│  │ (逻辑轴) │ (物理轴) │ (物理轴) │ (物理轴) │ (物理轴) │ (物理轴) │ │
│  └────┬─────┴────┬─────┴────┬─────┴──────────┴──────────┴──────────┘ │
│       │          │          │                                          │
│  ┌────▼──────────▼──────────▼──────┐    ┌────────────────────────┐    │
│  │   GantryCouplingController      │    │  GantryPowerController │    │

当前 UI 操作流程（龙门 X 轴）：
  ┌──────────────────────────────────────────────────────────────┐
  │ 1. 用户点「启用」按钮                                          │
  │    → GantryViewModel::startCoupling()                        │
  │    → GantryOrchestrator::startCoupling()                     │
  │    → EnsuringEnabled → WaitingEnabled → Coupling → Done      │
  │                                                               │
  │ 2. 用户操作点动/位置移动                                       │
  │    → JogOrchestrator / AbsMovePolicy / RelMovePolicy         │
  │    → tryGetAxis(X) ← 此时 X 已联动，可正常访问                 │
  │                                                               │
  │ 3. 用户点「停用」按钮                                          │
  │    → GantryViewModel::stopCouplingAndDisable()               │
  │    → Decoupling → WaitingDecoupled → Disabling → Done        │
  └──────────────────────────────────────────────────────────────┘

其他单轴（Y/Z/R）操作流程：
  ┌──────────────────────────────────────────────────────────────┐
  │ JogOrchestrator::startJog → EnsuringEnabled → PostEnableDelay│
  │ → IssuingJog → Jogging → [用户松手] → IssuingStop            │
  │ → WaitingForIdle → PostStopDelay → EnsuringDisabled → Done   │
  │                                                               │
  │ 即：自动使能 → 运动 → 自动掉电（延迟 500ms）                    │
  └──────────────────────────────────────────────────────────────┘
```

### 1.2 核心问题清单

| # | 问题 | 严重程度 | 描述 |
|---|------|---------|------|
| **P1** | X 轴必须手动先点「启用」才能移动 | 🔴 高 | 与 Y/Z/R 轴体验不一致：其他轴自动使能/掉电，龙门 X 需要用户手动操作 |
| **P2** | decoupled 时 X 位置信息不可读 | 🔴 高 | `tryReadAxis(X)` 也经过龙门语义拦截，未联动时无法获取 X 的位置用于界面显示 |
| **P3** | JogOrchestrator 中存在硬编码 `if (m_targetId == AxisId::X)` | 🟡 中 | 代码坏味道：在通用编排器中硬编码 X 特殊逻辑（跳过掉电阶段） |
| **P4** | X 的速度设置/位置移动目标设置受限 | 🟡 中 | `tryGetAxis(X)` 在 decoupled 时拒绝访问，无法设置 jogVelocity/moveVelocity/absTarget |
| **P5** | 单轴 Axis 模型不匹配龙门双轴语义 | 🟡 中 | Axis 是按"单个物理电机"设计的聚合根，但 X 是"逻辑组合轴"，未来还需要 X1/X2 独立控制 |
| **P6** | 未来需要手动拆分龙门 | 🟢 低（远期） | 需要支持拆分为 X1、X2 独立单轴控制的能力 |

### 1.3 问题根因分析

**根本原因**：`SystemContext::tryGetAxisInternal()` 中的龙门语义拦截层（Layer 1/2）将 **控制权限** 与 **数据读取权限** 混为一谈。

```
tryGetAxisInternal(X):
  if (gantry not synchronized) → reject X, X1, X2 全部拒绝
  if (coupled):
      reject X1, X2       ← 物理轴被锁定，合理
  else (decoupled):
      reject X             ← 逻辑轴不可用，但【过于激进】
                              → 连位置读取也拒绝了
```

**设计假设过时**：当初设计时认为"不联动就不应该访问 X"，这确实保证了**控制安全**，但忽略了**信息获取**的需求。UI 需要在任何状态下都能显示 X 的位置信息。

---

## 2. 设计目标

1. **取消「启用」按钮**：龙门 X 轴像 Y/Z/R 一样，只需操作点动/位置移动即可，底层自动完成使能+联动
2. **位置信息始终可读**：无论是否联动，X 的位置/速度/限位信息始终可通过 `tryReadAxis(X)` 获取
3. **控制权限保留**：X 的控制操作（点动/位置移动）仍需龙门联动成功后才允许执行（安全保证不变）
4. **代码解耦**：消除 JogOrchestrator 中 `if (m_targetId == AxisId::X)` 的硬编码
5. **架构可扩展**：为远期 X1/X2 独立控制留出扩展点

---

### 3.2 核心改动 1：SystemContext 读写分离

**目标**：X 的位置信息解耦龙门语义拦截。

```cpp
// domain/entity/SystemContext.h

// ★ 改动：tryReadAxis 对龙门轴放宽限制
bool tryReadAxis(AxisId id, Axis*& outAxis, ContextRejection& reason) {
    // 对龙门轴的读取：仅容器查找拦截（不经过龙门语义层）
    if (id == AxisId::X || id == AxisId::X1 || id == AxisId::X2) {
        // 跳过 GantryCouplingController 的联动状态检查
        // 仅做容器查找
        auto it = m_axes.find(id);
        if (it == m_axes.end()) {
            reason = ContextRejection::AxisNotRegistered;
            outAxis = nullptr;
            return false;
        }
        outAxis = it->second.get();
        reason = ContextRejection::None;
        return true;  // ✅ 始终允许读取龙门轴信息
    }

    // 非龙门轴走原有逻辑
    return tryGetAxisInternal(id, outAxis, reason);
}
```

**设计依据**：
- X 轴的位置数据来自 PLC 反馈，由 `AxisSyncService::sync()` 或 `applyPlcFeedback()` 写入，已经经过物理验证
- 读取位置不会产生任何硬件副作用，不存在安全风险
- 原有的"decoupled 禁止访问 X"是一种**过度约束**，混淆了读写权限

**注意**：`tryGetAxis()`（控制入口）保持现有拦截逻辑不变，确保控制安全。

### 3.3 核心改动 2：新增 GantryMotionOrchestrator

**目标**：抽象出龙门 X 运动的标准编排流程。

```cpp
// application/policy/GantryMotionOrchestrator.h

/**
 * @brief 龙门运动编排器基类
 *
 * 为龙门 X 轴的运动操作（点动/绝对定位/相对定位）提供标准编排模板：
 *   1. startMotion()  → 使能龙门电机 + 联动
 *   2. tick()          → 推进使能→联动→执行→等待完成→解耦→掉电
 *   3. cancelMotion()  → 中断当前运动
 *
 * 状态机：
 *   Idle → EnsuringEnabled → WaitingEnabled → Coupling → WaitingCoupled
 *   → IssuingCommand（子类实现） → Monitoring（子类实现）
 *   → Decoupling → WaitingDecoupled → PostDecoupleDelay → Disabling
 *   → WaitingDisabled → Done
 *
 * 与单轴 JogOrchestrator 的差异：
 *   - 单轴：使能 → 点动 → 掉电（500ms 延迟）
 *   - 龙门：使能+联动 → 点动 → 解耦+掉电（500ms 延迟）
 */
class GantryMotionOrchestrator {
public:
    enum class Step {
        Idle,
        // --- 前置阶段：使能 + 联动 ---
        EnsuringEnabled,      // 下发龙门电机使能命令
        WaitingEnabled,       // 等待电机使能完成
        Coupling,             // 下发联动指令
        WaitingCoupled,       // 等待 PLC 反馈联动完成

        // --- 运动阶段（子类重写钩子方法实现） ---
        IssuingCommand,       // 子类：下发具体运动指令（点动/绝对定位/相对定位）
        Monitoring,           // 子类：监视运动执行状态

        // --- 后置阶段：解耦 + 掉电 ---
        Decoupling,           // 下发解耦指令
        WaitingDecoupled,     // 等待 PLC 反馈解耦完成
        PostDecoupleDelay,    // 解耦后等待 500ms 确保物理状态稳定 → 然后掉电
        Disabling,            // 下发龙门电机掉电命令
        WaitingDisabled,      // 等待掉电完成

        // --- 终态 ---
        Done,
        Error,
        ErrorCleaning         // 运动中出错 → 解耦+掉电清理
    };

    // ========== 入口 ==========

    /**
     * @brief 启动龙门运动
     * @param axisId  目标轴（通常为 AxisId::X）
     * @param manager SystemManager 引用
     * @param groupName 分组名称
     */
    void startMotion(AxisId axisId, SystemManager& manager, const std::string& groupName);

    /// @brief 取消当前运动（提前进入解耦掉电流程）
    void cancelMotion();

    // ========== 逐帧驱动 ==========
    void tick();

    // ========== 状态查询 ==========
    Step currentStep() const;
    bool isDone() const;
    bool hasError() const;
    UseCaseError lastError() const;
    bool isBusy() const;  // 非终态且非 Idle

protected:
    // ========== 钩子方法（子类重写） ==========

    /// @brief 在 IssuingCommand 阶段执行（仅调用一次）
    /// @return true 成功，false 失败
    virtual bool issueCommand() = 0;

    /// @brief 在 Monitoring 阶段每 tick 调用
    /// @return true 运动完成（→ 进入解耦阶段），false 仍在运动中
    virtual bool isMotionCompleted() = 0;

    /// @brief 获取运动类型名称（用于日志）
    virtual std::string motionType() const = 0;

private:
    SystemManager* m_manager = nullptr;
    std::string m_groupName;
    AxisId m_axisId = AxisId::X;
    Step m_step = Step::Idle;
    UseCaseError m_lastError = std::monostate{};

    // --- 内部状态标志 ---
    bool m_enableSent = false;
    bool m_coupleSent = false;
    bool m_commandIssued = false;
    bool m_decoupleSent = false;
    bool m_disableSent = false;

    std::chrono::steady_clock::time_point m_decoupleDoneTime;
    static constexpr double kPostDecoupleDelaySeconds = 0.5;
    static constexpr double kEnableTimeoutSeconds = 3.0;

    std::string generateTraceId();
    std::string logPrefix() const;
};
```

```
Idle
  → EnsuringEnabled     (power.requestEnable(true) → 下发 GantryPowerCommand)
  → WaitingEnabled      (power.isEnabled() ?)
  → Coupling            (coupling.requestCouple(true) → 下发 GantryCouplingCommand)
  → WaitingCoupled      (coupling.isCoupled() ?)
  → IssuingCommand      (子类钩子 issueCommand())
  → Monitoring          (子类钩子 isMotionCompleted())
  → Decoupling          (coupling.requestCouple(false))
  → WaitingDecoupled    (!coupling.isDecouplingRequested() ?)
  → PostDecoupleDelay   (等待 500ms)
  → Disabling           (power.requestEnable(false))
  → WaitingDisabled     (!power.isEnabled() ?)
  → Done
```

### 阶段 6：远期扩展点——X1/X2 独立控制

> 此阶段不在本次实施范围，仅在设计上预留扩展点。

当需要手动拆分龙门时：

```
当前状态: Coupled → X1/X2 锁定，X 可用
拆分后:   Decoupled → X1/X2 解除锁定，可作为独立单轴控制，X 仅可读

实现路径：
  1. GantryViewModel 提供 splitGantry() / mergeGantry() 操作入口
  2. SystemContext 中的龙门语义层在 Decoupled 模式下已自动放开 X1/X2 访问
     （tryGetAxis 中 coupled → 拒绝 X1/X2；decoupled → 允许 X1/X2 通过）
  3. X1/X2 的 AxisViewModelCore 在 decoupled 时自动切换到单轴编排器
  4. X1/X2 的位置数据由 PLC 原始反馈提供（已在 Axis 实体中维护）
```

## 5. 架构对比

### 改造前

```
X 轴操作 = 手动「启用」→ 点动/定位 → 手动「停用」
          ↓
   GantryViewModel.startCoupling()  → 用户手动触发
   JogOrchestrator (单轴逻辑 + if X skip disable) → 丑陋硬编码
   GantryViewModel.stopCouplingAndDisable() → 用户手动触发
```

### 改造后

```
X 轴点动 = 用户长按点动按钮
          ↓
   AxisViewModelCore.jog()
   → isGantryAxis() ? GantryJogPolicy.startJog() : JogOrchestrator.startJog()
          ↓
   GantryJogPolicy (继承 GantryMotionOrchestrator)
   → 自动: 使能 → 联动 → 下发点动 → 运行中
   → 用户松手: 停止点动 → 等待Idle → 500ms延迟 → 解耦 → 掉电 → Done

X 轴绝对定位 = 用户设置目标 + 点击触发
          ↓
   AxisViewModelCore.triggerAbsMove()
   → isGantryAxis() ? GantryAbsMovePolicy.startAbsMove() : AbsMovePolicy.startAbs()
          ↓
   GantryAbsMovePolicy (继承 GantryMotionOrchestrator)
   → 自动: 使能 → 联动 → 触发绝对定位 → 等待完成 → 500ms延迟 → 解耦 → 掉电 → Done

X 位置信息读取 = 任何时候
          ↓
   AxisViewModelCore.absPos()
   → tryReadAxis(X) → ✅ 始终返回 Axis 实体（不再受龙门语义拦截）
```

## 7. 安全考量

### 7.1 不变的安全约束

| 约束 | 现状 | 改造后 | 说明 |
|------|------|--------|------|
| Layer 0：急停拦截 | `tryGetAxis()` 保留 | **不变** | 急停期间所有轴控制操作拒绝 |
| Layer 1：龙门同步检查 | `tryGetAxis()` 检查 | **不变** | 未同步前拒绝控制 |
| Layer 2：龙门语义 | `tryGetAxis()` 检查 | **不变** | Coupled → X1/X2 控制拒绝；Decoupled → X 控制拒绝 |
| 运动前使能+联动检查 | 手动 | **自动化** | GantryMotionOrchestrator 内部保证 |
| PLC 物理安全校验 | GantryCouplingController 检查 errorCode | **不变** | PLC 仍然是最终安全裁决者 |

### 7.2 放宽的约束（仅读取）

| 操作 | 改造前 | 改造后 | 理由 |
|------|--------|--------|------|
| `tryReadAxis(X)` decoupled 时 | ❌ 拒绝 | ✅ 允许 | 位置数据来自 PLC 反馈，读取无副作用 |
| `tryReadAxis(X1/X2)` coupled 时 | ❌ 拒绝 | ✅ 允许（read） | 便于界面同时显示三个轴的位置 |
| X 速度设置 `setJogVelocity()` | ❌ decoupled 时拒绝 | ✅ 允许（仅写寄存器） | 速度设置不触发运动，仅为下次运动准备 |

## 9. 风险与注意事项

| 风险 | 缓解措施 |
|------|---------|
| **X 位置数据在 decoupled 时可能无意义** | PLC 在 decoupled 时 X 位置寄存器可能为 0 或旧值；UI 应额外显示「未联动」状态提示 |
| **GantryMotionOrchestrator 与 GantryOrchestrator 共存** | 两者操作同一 GantryPowerController / GantryCouplingController，需互斥：同一时刻只能有一个编排器活跃 |
| **tryReadAxis 放宽后 UI 误用** | 确保 UI 层区分"读取"和"控制"入口；控制入口仍走 `tryGetAxis()` |
| **Performance** | 每次 `tick()` 增加一个 `isGantryAxis()` 分支判断，开销可忽略 |

## 10. 总结

本次重构的核心思想是：

1. **读写分离**：`tryReadAxis()` 不再拦截龙门轴信息读取，解决"界面看不到 X 位置"的问题
2. **策略模式**：引入 `GantryMotionOrchestrator` 基类 + 三个子策略，将龙门运动编排与单轴编排解耦
3. **自动化**：用户操作点动/定位时，底层自动完成「使能+联动→运动→解耦+掉电」完整流程，消除手动「启用」按钮
4. **可扩展**：为远期 X1/X2 独立控制预留架构空间

实施顺序建议：**阶段 1（读写分离）→ 阶段 2+3（龙门运动策略）→ 阶段 4（路由改造）→ 阶段 5（UI 适配）**，每阶段独立可测试、可回滚。

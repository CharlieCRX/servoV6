# 龙门联动失败无清理流程导致电机保持使能状态

## 日期
2026-06-03

## 问题概述

当龙门联动操作被 PLC 拒绝（例如 PositionToleranceExceeded），GantryOrchestrator 直接跳转到 Error 终态，**不执行任何清理操作**——电机保持使能状态，PLC 侧的耦合请求也未取消。导致硬件处于不一致的中间状态。

---

**关键证据**: 联动失败后，X1/X2 仍为 `Standstill`（使能状态），电机未被关闭。

## 根因分析

### 当前错误处理路径

```cpp
// GantryOrchestrator.h - WaitingCoupled step
case Step::WaitingCoupled:
    if (coupling.isCoupled()) {
        m_step = Step::Done;           // ✅ 成功：正常结束
    } else if (coupling.hasError()) {
        m_step = Step::Error;          // ❌ 失败：直接到 Error，无清理
        m_lastError = coupling.getLastError();
    }
    break;

case Step::Error:
    // 终态：tick 不再执行有效逻辑   ← 没有任何清理代码！
    break;
```

### 期望的错误处理路径

```
WaitingCoupled (检测到 errorCode=1)
  → Decoupling (下发解耦命令，取消 PLC 侧耦合请求)
  → WaitingDecoupled (等待 PLC 确认解耦完成)
  → Disabling (下发掉电命令)
  → WaitingDisabled (等待 PLC 确认掉电完成)
  → Error (上报错误给 UI)
```

### GantryViewModel 侧的影响

`advanceOrchestrator()` 在 `hasError()` 为 true 时立即停止推进：

```cpp
void GantryViewModel::advanceOrchestrator() {
    if (m_orchestrator->hasError()) {
        // 停止推进，不再 tick
        return;
    }
    m_orchestrator->tick();
}
```

如果 orchestrator 进入 Error 态，后续 tick 都不会再调用，因此无法在 Error 态执行清理逻辑。

---

## 修复方案

### 方案：在 Error 之前插入清理流程

在 `GantryOrchestrator` 中新增成员 `m_cleanupAfterError`，当 `WaitingCoupled` 检测到错误时，不直接跳转到 `Error`，而是进入清理流程：

1. **WaitingCoupled 检测到错误** → 保存错误到 `m_lastError`，设置 `m_cleanupAfterError = true`，跳转到 `Decoupling`
2. **Decoupling** → 下发解耦命令（与现有 `stopCouplingAndDisable` 流程相同）
3. **WaitingDecoupled** → 检查 `m_cleanupAfterError`，跳转到 `Disabling`
4. **Disabling** → 下发掉电命令
5. **WaitingDisabled** → 检查 `m_cleanupAfterError`，清除标志，跳转到 `Error`

### 修改的文件

| 文件 | 修改内容 |
|------|----------|
| `application/policy/GantryOrchestrator.h` | 新增 `m_cleanupAfterError` 成员；修改 `WaitingCoupled` / `WaitingDecoupled` / `WaitingDisabled` 步骤逻辑 |

### 修改后的关键代码

```cpp
// 新增成员
bool m_cleanupAfterError = false;

// WaitingCoupled step
case Step::WaitingCoupled:
    if (coupling.isCoupled()) {
        m_step = Step::Done;
    } else if (coupling.hasError()) {
        // 保存错误，进入清理流程
        m_lastError = coupling.getLastError();
        m_cleanupAfterError = true;
        LOG_WARN(... "WaitingCoupled -> Decoupling (cleanup after error)");
        m_step = Step::Decoupling;
    }
    break;

// WaitingDecoupled step
case Step::WaitingDecoupled:
    if (!coupling.isDecouplingRequested()) {
        if (m_cleanupAfterError) {
            m_step = Step::Disabling;
        } else if (m_disableAfterDecouple) {
            // 原有 stopCouplingAndDisable 流程
            ...
        } else {
            m_step = Step::Done;
        }
    }
    break;

// WaitingDisabled step
case Step::WaitingDisabled:
    if (!power.isEnabled()) {
        if (m_cleanupAfterError) {
            m_cleanupAfterError = false;
            m_step = Step::Error;
        } else {
            m_step = Step::Done;
        }
    }
    break;
```

### 为什么不在 Error 态执行清理

1. `GantryViewModel::advanceOrchestrator()` 在 `hasError()` 时停止推进
2. 在 Error 态执行清理需要修改 ViewModel 的停止逻辑，增加复杂性
3. 在状态机流转中完成清理更符合编排器"逐帧推进"的设计模式
